# Setup wizard (`lesysbot/setup/`) and the installer (`scripts/install.sh`)

The installer is **self-contained and curl-pipeable** — `curl -fsSL https://lesysbot.github.io/install.sh | sh` is the documented install, and the published copy is synced from `scripts/` into the docs site's `content/static/` by its `scripts/import-docs.js`. Each one: finds a Python ≥3.11 (probing `python3.13…python`, gated on `import venv` too because Debian splits `python3-venv` out) or fetches one with **uv** when there is none; builds a venv at `~/.local/share/lesysbot/venv` — deliberately *not* under `~/.lesysbot`, which every doc calls safe to delete; `pip install`s `lesysbot[telegram,discord]` from a GitHub archive zip (no git, no PyPI; the leaf extras rather than the self-referential `[all]`); links `~/.local/bin/lesysbot`; adds that to `~/.profile`/`~/.bashrc`/`~/.zshenv` inside a marked block `--uninstall` removes exactly; installs Ollama and pulls the model; then runs **`lesysbot setup --yes`**. Run from a checkout with no `--ref`/`--version` they install *that checkout*, so a change can be tested without pushing. They also carry `--uninstall`/`--purge`, which is why the installer copies itself into the install dir. **`install.sh` is POSIX `sh`**, since the pipe is `| sh` and that is dash on Debian/Ubuntu — no `[[ ]]`, no arrays, no `BASH_SOURCE` (a `script_dir()` derived from `$0` replaces it), and `set -o pipefail` only behind a subshell probe; `tests/test_shell_portability.py` (`POSIX_SCRIPTS`, `BASHISMS`) and CI's `shellcheck --shell=sh --severity=warning` enforce it. The wizard itself is **one cross-platform Python implementation** in `lesysbot/setup/`, shared by every OS, and `--repo` is development-only — a normal install seeds from the content bundled in the wheel (`paths.bundled_dir()`). `lesysbot setup` also runs standalone at any time to reconfigure an existing install. It writes `config.yaml` and seeds `tools/`, `dashboards/`, `catalog.json` and the `dashboard/` stack into **`~/.lesysbot/`** (`user_dir()`, overridable via `LESYSBOT_HOME`) and points the service's `WorkingDirectory` there; `tools_dir`/log paths stay relative in the written config and anchor to `~/.lesysbot` at load time. Seeding goes through the artifact installer's rules and records packages as `bundled: true`, so a fix to a bundled package reaches people who already have it. The Grafana dashboard is **default, not optional**: after config it always runs `apply.start_dashboard` (see `dashboard/CLAUDE.md`). `scripts/uninstall.sh` remains for installs predating the current installer; both it and `install.sh --uninstall` keep `~/.lesysbot` unless asked to purge.

Module layout — `ui.py`: Rich-panel widgets (`InteractiveUI.menu/text/confirm_yn`) rendered in a transient `Live` that leaves a one-line `❯ label · answer` echo behind; `read_key()` reads **raw bytes from the stdin fd via `os.read` inside a `raw_mode()` (cbreak) context held for the whole widget** — per-keypress termios toggling loses queued bytes to the canonical line buffer (fast typing/paste kept only the first char), and `sys.stdin` readahead hides bytes from `select()`, desyncing escape parsing. Escape sequences are collected byte-by-byte with a 0.25 s timeout and whole CSI sequences are slurped so Home/Del/F-keys can't leak. `text(..., secret=True)` masks the typed chars/default-hint/echo with `*` (password entry — the Grafana password uses it; `PlainUI` reads it via `getpass`). `PlainUI` is the no-terminal fallback (numbered "type a number" menus via `input()`, EOF → default + `eof` flag). **`AutoUI(PlainUI)`** is unattended mode's single seam: every widget returns the offered default and stdin is never read, and it keeps `interactive = False`, which `apply.py`'s Grafana branches *already* consult (`auto = True` unless a human is watching) — so `setup --yes` sets the dashboard up with **no change to those functions**. It sets `unattended = True`, which only `ask_grafana_credentials` reads. `make_ui(unattended=False)` picks: `AutoUI` when asked, else `InteractiveUI`/`PlainUI` by `isatty`. `wizard.py`: `WizardState` dataclass + the step chain (`step_llm`/`step_messaging`/`step_autostart` + `run_steps`, `show_summary`/`step_summary`), `ask_allowed_ids()` shared by the Telegram and Discord branches, and the Ollama picker. `apply.py`: config template, package seeding (`seed_tools`/`seed_dashboards`/`seed_catalog`), the Grafana stack (`seed_dashboard`/`start_dashboard`, gated by `_docker_running`), service setup (`setup_service_linux`, a `systemd --user` unit), and `read_config_state()`; the service and stack functions take a `runner` param so tests record instead of touching the host. `unattended.py`: `state_from_env()` builds a complete `WizardState` from defaults + `LESYSBOT_SETUP_*` (never shelling out to `ollama` — the installer already pulled the model), and `generated_password()`; a missing required value calls `_abort`, which prints the variable to set and raises `SetupAborted(1)`. `cli.py`: argparse wiring (`--yes`, `--reconfigure`, `--skip-dashboard`) + the top-level flow (seed → service → `start_dashboard` → epilogue); dispatched in `__main__.main()` before the artifact CLI.

- **Navigation contract**: ↑/↓ move, Enter/→ confirm, number keys jump; when a menu has a "← …" entry, ←/Esc confirms it directly (inert otherwise); Esc at a text prompt returns `None` and the step loops re-show that step's menu with answers intact. The summary is a menu (Apply / Change LLM backend / Change how to reach LeSysBot / Change startup behaviour (service only) / Quit); nothing is written until Apply. Revisited steps offer previous answers as defaults — except LLM follow-ups, cleared when the backend choice changes. The kept-config path (existing config not overwritten) has no chain — just y/N service + apply questions; its summary is filled by `apply.read_config_state()`, which parses the existing `config.yaml` back into a `WizardState` (missing keys fall back to the `LLMConfig` model defaults the bot would actually run on), so it shows the install being kept instead of a blank state.
- **Messaging step is framed as "How to reach LeSysBot"**: option 1 is the terminal (default → `provider: cli`); Telegram/Discord are additive remote channels. A **background service (a `systemd --user` unit) is installed for every provider** (`WizardState.needs_service` is always True) — it serves the always-on control panel, and additionally runs the bot when a remote provider is configured; with `cli` it serves the panel and idles. Both remote providers require a non-empty allow-list — `ask_allowed_ids()` re-asks until valid, and in `PlainUI` mode aborts (`SetupAborted`) when piped input runs dry (`ui.eof`). The wizard ends with a provider-aware "How to use" epilogue that names `lesysbot setup` for reconfiguring.
- **Unattended (`--yes`)**: an existing `config.yaml` is **kept** unless `--reconfigure` (which is what makes re-running the installer a safe upgrade), `auto_start` defaults True, and the Apply confirmation is skipped. The Grafana password is generated when none is set, falling back **previous `grafana.env` → `LESYSBOT_SETUP_GRAFANA_PASSWORD` → generated**, in that order: Grafana only honours `GF_SECURITY_ADMIN_PASSWORD` on an empty volume, so rotating it on a re-install would lock LeSysBot out of its own dashboard. It is never printed — `_persist_grafana` prints the `grep` command instead.
- **`LESYSBOT_SKIP_SERVICE=1`** short-circuits `apply.setup_service` (and the installer's uninstall). The `systemd --user` unit lives at a fixed per-user path that **`LESYSBOT_HOME` does not relocate**, so without it a run against a scratch home replaces the real machine's service. Set it for every manual test.
- **The service path stops-and-replaces + `restart`s** so a changed config actually takes effect. There is no stale-service cleanup any more: every setup installs the service, so there is never a leftover one to remove (uninstall is `scripts/uninstall.sh`). `apply.setup_service` takes a `runner` like the service functions, so tests never touch the host's systemd.
- **No sudo, ever** — and this holds project-wide, not just for the wizard. "Enter through the prompts" must stay password-free, and **no tool may require root either**: never shell out through `sudo`, never ship a sudoers script, prefer the unprivileged source of the same fact, and where none exists say so in the reply instead of elevating (`docs/writing-tools.md`, "Never require root"). The bundled `power` package stays because `shutdown` goes through logind/polkit for a local session. The **one** documented edge is Ollama's own installer, which needs root on Linux: `install.sh` runs it only when already root or `sudo -n true` succeeds, and otherwise prints the two lines and carries on (`--with-ollama` overrides).

Tests: `tests/test_setup_wizard.py` drives the chain through a scripted `FakeUI` (navigation, defaults preservation, backend-switch clearing, Telegram/Discord validation and EOF, summary jumps, `read_config_state` round-trips), plus config/package seeding, dashboard start (the auto-start-vs-manual menu, the Docker-not-ready fixes, `LESYSBOT_SKIP_DASHBOARD`, no-dir no-op; `_ran_script` matches on the script argument rather than the whole command line, because a `tmp_path` readily contains the word 'start'), the Grafana credential prompt + `grafana.env`/`dashboard/.env` persistence, and service functions via a recording runner (the `setup_cli.run` tests stub `apply.setup_service` outright, so a test run can never install a real systemd service; hermetic through `LESYSBOT_HOME`/`HOME` monkeypatching; `shutil.which` monkeypatched for the docker probes, `FakeUI.messages` records printed instructions). `test_config.py` also covers `parse_env_file`/`load_grafana_env` (file→env, explicit env wins). Unattended mode is covered by its own block at the end of that file (AutoUI never reading stdin, the default config, Telegram from env, aborts naming the variable, keep-vs-`--reconfigure`, generated/reused/never-printed Grafana password, `parse_allowed_ids`), and `tests/test_main.py` pins the `chat` → `--provider cli` rewrite. Every prompt is documented in `docs/getting-started.md`. Naming note: `lesysbot/setup/` is the *install wizard*; `lesysbot/artifacts/` is the *package installer* — unrelated modules.
