# Dashboard stack (`dashboard/`)

`dashboard/` is a **standard, self-contained Prometheus + Grafana stack** that records CPU / memory / disk / network (per-interface, so Ethernet vs Wifi) / temperatures / NVIDIA GPU as time series. It is **default, not optional**: `lesysbot setup` seeds it into `~/.lesysbot/dashboard` (`apply.seed_dashboard` — skips `bin/`/`run/`/`native/`, copies `.env` from the example, and **refreshes shipped files whose contents differ while never touching the user's**, the split being `DASHBOARD_KEEP = (".env", "prometheus")`: ports/Grafana login and hand-added scrape targets are seeded once and then left alone forever, everything else is program code whose installed copy has no value except to be current. Unlike `seed_tools` it deliberately doesn't bail out on `dst.exists()`. This went through two bugs, both of which are regression-tested in `tests/test_setup_wizard.py`: bailing out whenever `dashboard/` existed meant a stack that *gained* a file could never deliver it (a machine set up before `install-macos.sh` existed kept falling back to the manual Grafana instructions), and then adding-but-never-refreshing made the shipped scripts and dashboards **unpatchable** — every existing install silently kept running last release's code, so a fix to `install-macos.sh` or a regenerated dashboard reached nobody who already had the file. Re-running `lesysbot setup` is the upgrade path, so it has to actually deliver fixes) and then runs `apply.start_dashboard`, which is **OS-specific and never fatal**: **Linux** — if Docker is running (`_docker_running` = installed + `_compose_ok` + `_daemon_ok`) it asks a menu (auto-start the bundled stack now via `_run_bundled_stack` = `bash start.sh up`, vs do-it-manually); if Docker isn't ready it prints the exact no-sudo fix (install Docker Engine / start daemon / join `docker` group) plus the native-Grafana alternative. **macOS** — deliberately **does not require Docker Desktop**, and is fully automatic instead: `_grafana_macos` asks the same auto/manual menu, then `_run_brew_stack` runs `bash dashboard/scripts/install-macos.sh up`, which `brew install`s `grafana`/`prometheus`/`node_exporter`, generates `dashboard/native/`, points the brew services at it, sets the admin password and starts all three under `brew services`. With no Homebrew (`_brew_ready`) there is nothing to automate, so it names `brew.sh` (`BREW_INSTALL`) and falls through to `_grafana_manual_instructions`. **Windows** — deliberately **does not require Docker Desktop**: `_grafana_manual_instructions` warns and instructs a native Grafana install from `grafana.com/grafana/download` (`GRAFANA_DOWNLOAD`) and how to connect it (auto-detected on `localhost:3000`, else `LESYSBOT_GRAFANA_URL`), and only mentions the one-command bundled stack as a shortcut when Docker happens to be running. `LESYSBOT_SKIP_DASHBOARD` skips the whole step (unattended installs). **Each OS flow asks *how* first (the auto/manual menu on Linux), then the Grafana username+password** LeSysBot should use (`ask_grafana_credentials`, defaults admin/admin, prev values from the saved file offered as defaults; the password prompt passes `secret=True` so `ui.text` masks the typed chars, the default hint, and the left-behind echo — never printed back anywhere either). The saved **URL is derived, never hardcoded**: `apply.grafana_port()` reads `GRAFANA_PORT` from the seeded `dashboard/.env` (the one place the port is set — it's what a user changes when something else owns 3000) and `default_grafana_url()` turns it into `http://localhost:<port>`, keeping a previously saved *non-local* URL (a deliberate remote Grafana) but letting the stack's port override a saved `localhost:` one — otherwise a stack on 3001 kept being advertised on 3000, where the impostor service answers. `_persist_grafana` then `write_grafana_env`s them to `~/.lesysbot/grafana.env` (0600) as `LESYSBOT_GRAFANA_{URL,USER,PASSWORD}` and `_apply_creds_to_stack_env`s the same admin login into the bundled `dashboard/.env` (`GF_SECURITY_ADMIN_*` first-boot only). `grafana.env` is read back at bot startup by `paths.load_grafana_env()` (called from `__main__._load_settings`, `os.environ.setdefault` so an explicit env wins; the password/token are then `add_secret`ed for log redaction) — that's how the `share_dashboard` tool and `status.detect_grafana` authenticate. `paths.parse_env_file` is the shared flat `KEY=VALUE` parser. It is **not part of the Python package** (not under `lesysbot/`, so hatchling never bundles it) and it does **not** reintroduce a listener into the bot — the stack runs as its own processes (containers, or brew services on macOS), everything binds **`127.0.0.1` only**, and it needs **no sudo** (`docker compose` and `brew` both run unprivileged; upholds the same security/no-root stance as the rest of the repo). `uninstall.sh` detects which stack is present and offers to stop it — `install-macos.sh down` (brew services stopped, formulae left installed, with the `brew uninstall` line printed) and/or `start.sh down` (no `-v`, so Docker volumes survive); macOS can have both, so it asks once and stops whatever it finds. Docs live in `dashboard/README.md`; the agent-facing skill is `skills/manage-dashboards/`; discoverable from root `README.md` (features + the "What next?" table) and `docs/README.md` (Keep it running).

**Two compose files, because host metrics need different plumbing per OS:**
- `docker-compose.linux.yml` — **Linux**: Prometheus + Grafana + `node-exporter` (+ `nvidia-exporter` under `--profile gpu`) all on the **host network**, bound to localhost. Host networking is mandatory: `/proc/net/dev` is network-namespace-scoped, so a bridge container reports its own `eth0` instead of the host's real NICs; running everything host-net + localhost also sidesteps the `ufw`/iptables block on container→host traffic.
- `docker-compose.yml` — **macOS/Windows** (Docker Desktop): Prometheus + Grafana on a bridge; exporters run **natively** (auto-downloaded by `scripts/run-exporters.{sh,ps1}`) and are scraped via `host.docker.internal` (Docker Desktop's VM can't see the host otherwise).

**Plus a third, Docker-free path on macOS — `scripts/install-macos.sh`**, which is what `lesysbot setup` runs there (the compose file above stays for anyone who prefers containers; the script refuses to start when it sees `lesysbot-*` containers running, since both bind the same ports). It brew-installs `grafana`/`prometheus`/`node_exporter` and runs them under `brew services`, so the whole stack survives a reboot without a daemon. Everything it *generates* lands in `dashboard/native/` (git-ignored — the paths are absolute and machine-specific), rewritten from scratch on every run: a Prometheus scrape config on plain `localhost` (no `host.docker.internal` hop), Grafana provisioning with the datasource URL **baked in** (there is no compose to interpolate `${PROM_URL}`), and a dashboards dir holding **only one** JSON — the file provider loads every JSON it finds, so the shared `grafana/dashboards/` dir would provision the Windows one too. **That JSON is generated for the host, not copied**: the script detects the hardware (`uname -m` → `MAC_ARCH`/`MAC_KIND`, `has_nvidia` = `nvidia-smi` on PATH), turns it into a capability list via `dashboard_caps()` and runs `gen-dashboards.py --host macos --have <caps> --out …`, falling back to copying the portable `system-overview-linux-macos.json` (with a warning naming the reason) when there is no `python3` or the generator fails. That call must **never** swallow the generator's stderr and `install-macos.sh` must keep its sourcing guard: it once passed the removed `--macos/--intel/--nvidia` flags into `>/dev/null 2>&1`, so argparse's exit-2 was invisible and every Mac silently ran the portable dashboard — `start.sh` survived the same CLI change only because `tests/test_start_detect.py` pinned its flags against the generator, which is why `tests/test_install_macos.py` now does the same here. The reason is the reported symptom: on a Mac the portable dashboard's Linux hwmon rows and its NVIDIA row can never fill, and an empty panel is indistinguishable from a broken one. NVIDIA is gated on `nvidia-smi` rather than on hardware because `nvidia_gpu_exporter` shells out to it — no driver means nothing can be scraped (`nvidia_hardware_present()` via `system_profiler` exists only to *explain* the omission), and the same flag now gates the `nvidia_gpu` scrape job, which previously pointed at a port nobody served. Section 4c starts that exporter through `run-exporters.sh nvidia` (a verb added for this) with `EXPORTER_BIND=127.0.0.1`, since that script's macOS default is `0.0.0.0` for the Docker Desktop VM hop. Generating per host is what keeps `gen-dashboards.py` the single source of truth without committing a JSON per hardware combination; `tests/test_gen_dashboards.py` pins the inclusion/exclusion decisions and fails when the committed JSONs go stale. Wiring the brew formulae up takes three different mechanisms, each forced by how the formula is packaged: `prometheus`/`node_exporter` read their flags from `$(brew --prefix)/etc/<name>.args` (a `$(<file)` expansion, so those files **cannot carry a comment** marking them ours — hence the `.args.lesysbot` stamp file the backup check diffs against, which is what stops a re-run from "backing up" its own output); Grafana is launched with a fixed `--config`, so the script instead appends a delimited `;;; BEGIN LeSysBot ;;;` block to `grafana.ini` (later sections/keys win in Grafana's ini parser, verified — so the shipped file is never edited, only appended to, and the block is replaced wholesale on re-run); and the admin password goes through `grafana cli admin reset-admin-password --password-from-stdin` with the server stopped, because `[security] admin_password` in `grafana.ini` only applies when the DB is first created (so it can't fix an existing Grafana) and would mean a cleartext password in a shared `etc/` file. Ports/credentials come from `dashboard/.env`, the same file the compose stacks read, so `apply.grafana_port()` keeps deriving the saved URL correctly. It also installs the **macOS metrics collector**: `node_exporter` has no GPU support on macOS and its `thermal` collector exposes CPU *throttling* ratios (`node_thermal_cpu_speed_limit_ratio`, `…_scheduler_limit_ratio`, `…_available_cpu`) rather than any temperature, through an Intel-only API (on Apple Silicon it reports `node_scrape_collector_success{collector="thermal"} 0`) — hence the Intel-only throttling panels in `temps_section_macos`. So the GPU and temperature rows were empty on every Mac regardless of how the stack started. `scripts/macos-metrics.py` (stdlib only) reads `ioreg` for Apple GPU utilization/memory (`IOAccelerator` → `PerformanceStatistics`) and battery temperature (`AppleSmartBattery`, hundredths of a °C), writes `macos_*` samples **atomically** (tmp + rename, since node_exporter may read mid-write) into `native/textfile/`, and node_exporter serves them via `--collector.textfile.directory`. A **launchd agent** (`com.lesysbot.macos-metrics`, `StartInterval` 15 s) re-runs it — a one-shot script needs a timer, and launchd also brings it back after a reboot like the brew services around it; its interpreter is pinned to brew's or `/usr/bin/python3` rather than whatever `command -v python3` finds, because launchd has a minimal PATH and a conda/venv python can vanish. CPU/GPU **die** temperatures are deliberately absent: Apple exposes them only via IOReport (private framework) or root-only `powermetrics`, so the collector opportunistically reads `smctemp`/`macmon` if the user installed either, and the dashboard tiles stay empty otherwise (their panel descriptions say so, since an empty tile otherwise reads as a broken dashboard) — the no-sudo rule wins over completeness. Section 1a of the installer now **offers** to install one, arch-aware (`macmon` is `arch: :arm64`, so an Intel Mac is only offered `smctemp`, and an explicit `LESYSBOT_TEMP_HELPER=macmon` there is downgraded to `smctemp`). The prompt **defaults to no**, is skipped entirely when stdin isn't a TTY (`[ -t 0 ]` — the wizard runs it through `subprocess.run`, so it inherits a terminal when there is one), can be answered up front with `LESYSBOT_TEMP_HELPER=macmon|smctemp|none`, and a failed `brew install` warns rather than failing the stack. Neither helper may become a dependency: both are **personal taps, not homebrew-core**, and they fail on ordinary machines — brew refuses them outright on an outdated Xcode, and `smctemp` compiles from source so it also needs Command Line Tools (`macmon` at least ships a prebuilt binary, but is `arch: :arm64` only). That "offer, never require" shape is the whole point; making either a hard step would break the enter-through-the-prompts install on a machine with old developer tools. macmon's JSON layout is not a stable contract, so `_find_temps` walks the parsed object matching on key *names* anywhere in the tree rather than a fixed path — a pinned path would silently break on upgrade into an empty panel nobody notices. `tests/test_macos_metrics.py` loads the script by path (it's outside the wheel), stubs `_run`, and pins the parsing against recorded `ioreg` output plus several plausible macmon shapes, so it verifies on Linux CI where neither tool can exist. Because a textfile keeps being served after the writer dies, the collector emits `macos_metrics_last_run_timestamp_seconds` (formatted with `repr()`, not `%g` — 6 significant digits mangles a Unix timestamp by hours) and `status` reports the sample's age rather than merely that the file exists. It **preflights the ports** after stopping its own services (so a re-run doesn't flag itself) and `die`s naming the process that holds one — a busy port is otherwise silent, since `brew services` just parks the service in `error` state and the dashboard renders empty panels; 9090 is a common clash (VS Code listens there). For the same reason the closing report verifies **Prometheus as well as Grafana** and the script exits non-zero when either is down, so `_run_brew_stack` reports it rather than claiming success. Two `set -e` traps to respect when editing it: `set -o pipefail` means `lsof` exiting 1 on a free port propagates out of `owner="$(port_owner …)"` and kills the script before any caller sees the empty result (hence the `|| true` inside `port_owner`), and it targets **bash 3.2** (macOS' `/bin/bash`), where a bare `$var` immediately followed by a non-ASCII character parses as part of the variable name — so interpolations adjacent to `…`/`—` must be braced.

The Grafana datasource URL is `${PROM_URL}` (Grafana interpolates env vars in provisioning files); each compose injects it (`http://prometheus:9090` bridge vs `http://127.0.0.1:9090` linux), so one datasource file serves both. Grafana provisions **only the OS-relevant dashboard**: each compose mounts one JSON to `/var/lib/grafana/dashboards/system-overview.json` (the bridge `docker-compose.yml` selects via `${DASH_JSON:-system-overview-linux-macos.json}`, which `start.ps1` sets to the Windows file), so a Linux/macOS host never shows an empty "System Overview — Windows" (and vice-versa). `dashboards.yml` has `disableDeletion: false`, so switching removes the other one on next boot. `scripts/start.{sh,ps1}` are the OS-aware one-command up/down entrypoints. **Dashboards are generated** — edit `scripts/gen-dashboards.py` (stdlib only) and regenerate, never hand-edit the JSON under `grafana/dashboards/`. The generator has two modes: bare, it rewrites the two committed **portable** JSONs; `--host {linux,macos,windows} --have <caps> --out PATH` emits one **host-specific cut** (`build_linux`/`build_macos`/`build_windows` via `build_for`), which is what every start script now runs. Shared panels live in `cpu_section`/`swap_section`/`disk_section`/`network_section` so the cuts can't drift from each other. `CAPABILITIES` is the per-host vocabulary and an unknown capability is an argparse error — a typo in a start script must fail loudly rather than silently drop a dashboard row. Each cut reuses the portable dashboard's `uid` (`lesysbot-node`, or `lesysbot-windows`) so re-running a start script *replaces* the dashboard instead of accumulating near-duplicates.

**Each start script probes before generating**, because a panel querying a metric the host can't produce is visually identical to a broken panel — that ambiguity is the bug the whole mechanism exists to remove. `start.sh` (`detect_capabilities_linux`) reads chip names from `/sys/class/hwmon/*/name` (`coretemp|k10temp|zenpower|cpu_thermal` → `cpu_temp`, `nvme|drivetemp` → `disk_temp`, `amdgpu` → `amd_gpu`; AMD GPU temperature comes from hwmon and needs **no exporter**, unlike NVIDIA) plus `/sys/class/thermal/thermal_zone0` and `nvidia-smi`; `start.ps1` asks the **running** `windows_exporter` whether it actually serves `windows_thermalzone_*`, since that is a firmware property and no static rule gets it right. **NVIDIA is keyed on `nvidia-smi` everywhere, never on the card** (`nvidia_gpu_exporter` shells out to it, so a driverless GPU is unscrapeable); `lspci`/`Win32_VideoController`/`system_profiler` are consulted *only* to explain the omission and name the driver to install. Both scripts then print an "optional add-ons" block (the exact `modprobe` for a missing Linux sensor driver, LibreHardwareMonitor on Windows, a die-temp helper on macOS) — suggestions, never run for the user, and suppressed inside a VM (`is_virtual`) where the advice would be a dead end. Generated files are `grafana/dashboards/generated-*.json` (git-ignored), selected via `DASH_JSON` — `docker-compose.linux.yml` gained the same `${DASH_JSON:-…}` indirection the bridge compose already had. Falling back to the committed portable JSON (no `python3`) always warns, because "whole rows are empty" then has a different cause than a real fault. `start.sh` `return 0`s when sourced instead of executed, which is the seam `tests/test_start_detect.py` drives against a fixture `/sys` tree via `SYSFS_ROOT` — so Linux-only detection logic is verified on macOS and Linux CI alike. GPU metrics are `nvidia_smi_*` (labeled by `uuid` only → legends use `{{uuid}}`); temperatures come from `node_exporter` `hwmon`/`thermal_zone` via a `group_left` join onto `node_hwmon_sensor_label`/`node_hwmon_chip_names` (CPU = `coretemp|k10temp|cpu_thermal`, disk = `nvme|drivetemp`), so temperature coverage is Linux-rich, battery-plus-optional-die on macOS (see the collector above), and ACPI-best-effort on Windows. The macOS additions follow the existing split: the CPU/GPU temperature **stat tiles** `or` the `macos_*` series onto the hwmon ones (exactly one side has data on a given host, so one tile serves both), but Apple GPU gets a **row of its own** (`gpu_section_apple`) rather than being `or`-ed into the NVIDIA panels — the two sources label series differently (`uuid` vs `engine`), so a merged panel would lose its legend on one OS. It's empty on Linux just as the NVIDIA row is empty on a Mac — on the *macOS* cut that row is instead the main GPU row (retitled via `gpu_section_apple(title=…)`) and the NVIDIA one is omitted. Swap is **not** Linux-only, contrary to what that panel's description used to claim: macOS names the metrics `node_memory_swap_{used,total}_bytes` against Linux' `SwapFree`/`SwapTotal`, so the portable panel `or`s both. `dashboard/{bin,run,native}/` and `.env` are git-ignored.

**OS-adaptation is the whole point, so several things auto-select at runtime.** `start.{sh,ps1}` preflight Docker (installed / Compose v2 / daemon reachable) and fail with a fix-it message instead of a stack trace. On Linux, `start.sh` picks the **GPU** path automatically: `--profile gpu` (containerised `nvidia_gpu_exporter`) when `docker info` shows the `nvidia` runtime, else a **native** GPU exporter via `run-exporters.sh` — so a GPU box without the nvidia-container-toolkit still gets GPU metrics instead of a crash-looping container. The shared "Linux / macOS" dashboard works on **both** because macOS `node_exporter` uses different metric names — memory panels `or`-fall-back (`node_memory_MemAvailable_bytes`/`MemTotal_bytes` → `node_memory_active/wired/compressed/total_bytes`), and the Windows total-RAM metric `or`s `windows_cs_physical_memory_bytes`/`windows_memory_physical_total_bytes` across exporter versions. macOS-absent readings (swap, disk I/O, temperatures) just stay empty. When editing dashboard queries, keep the `or`-fallbacks — dropping one silently blanks a panel on the other OS.

The bundled **`tools/share-dashboard/`** package bridges the stack back to the bot: "share me the dashboard" publishes a public Grafana **snapshot** to `snapshots.raintank.io`. It builds the snapshot itself — pulls the dashboard model from Grafana, replays each panel's Prometheus queries via Grafana's datasource proxy (`/api/datasources/proxy/uid/<ds>/api/v1/query_range`), and bakes the results into **each panel target** as a `queryType:"snapshot"` frame list (modern Grafana data-frame JSON: `{schema:{fields:[Time, Value(labels)], meta}, data:{values:[[ms…],[…]]}}`, one entry per series) so the public copy renders on Grafana 11 without reaching back to your Prometheus. **Critical:** the older top-level `panel.snapshotData` format does *not* render on Grafana 11 — the data must live on each target, and the request is POSTed to **Grafana's own `/api/snapshots`** with `{dashboard, name, expires, external:true}` (auth'd), letting Grafana relay it to raintank and return the public `url` (plus a Grafana-side `deleteUrl`; delete is a GET on it). POSTing the baked model straight to raintank instead produces empty panels. **Because we now publish *through* Grafana, Grafana is the snapshot registry** — so `list_snapshots`/`delete_snapshot` build a combined list (`_combined_snapshots`): **`GET /api/dashboard/snapshots`** (Grafana's own `/dashboard/snapshots` page, authoritative) **plus** any *unexpired* snapshots recorded in `~/.lesysbot/dashboard_snapshots.json` that Grafana has since pruned ("orphans", flagged in the listing). Grafana prunes external-snapshot rows **aggressively** (snapshots created minutes apart were already absent from `/api/dashboard/snapshots` while only the newest survived), so a listing that trusted only the local file over-reported ghosts, while one that trusted only Grafana would hide still-live public links — hence the merge. `list_snapshots` prunes the local file of **expired** entries only (never live ones — that would discard their deleteKey). **Deletion is dual (`_delete_everywhere`):** `DELETE /api/snapshots/<key>` on Grafana when it still knows the key (also asks raintank to drop it), **and** a direct `GET {raintank}/api/snapshots-delete/<deleteKey>` — the key point being **the `deleteKey` returned at creation is raintank's own** (verified: it deletes on raintank independent of Grafana), so orphans Grafana forgot are still removable as long as we kept the deleteKey. raintank may serve a CDN-cached copy for up to ~1h after deletion (its delete response says so). Grafana creds come from `LESYSBOT_GRAFANA_USER`/`_PASSWORD`/`_TOKEN` (defaults `admin`/`admin`); its **location** is resolved by `_resolve_grafana` like `status.detect_grafana` — `LESYSBOT_GRAFANA_URL` only when `_is_grafana` confirms Grafana answers there, else probe `_candidates()` (the local `dashboard/.env` `GRAFANA_PORT` first, then 3000/3001). Trusting the override blindly meant a stale saved URL POSTed snapshots at whatever else now owns that port. Tests are network-free (`tests/test_share_dashboard.py` monkeypatches the module's `_grafana`/`_query_range`/`_post`/`_delete`/`_get`).
