# Dashboard stack (`dashboard/`)

`dashboard/` is a **standard, self-contained Prometheus + Grafana stack** that records CPU / memory / disk / network (per-interface, so Ethernet vs Wifi) / temperatures / NVIDIA GPU as time series. It is **default, not optional**: `lesysbot setup` seeds it into `~/.lesysbot/dashboard` (`apply.seed_dashboard` — skips `bin/`/`run/`/`native/`, copies `.env` from the example, and **refreshes shipped files whose contents differ while never touching the user's**, the split being `DASHBOARD_KEEP = (".env", "prometheus")`: ports/Grafana login and hand-added scrape targets are seeded once and then left alone forever, everything else is program code whose installed copy has no value except to be current. Unlike the old `seed_tools` it deliberately doesn't bail out on `dst.exists()`. This went through two bugs, both regression-tested in `tests/test_setup_wizard.py`: bailing out whenever `dashboard/` existed meant a stack that *gained* a file could never deliver it, and then adding-but-never-refreshing made the shipped scripts and dashboards **unpatchable** — every existing install silently kept running last release's code, so a fix to `start.sh` or a regenerated dashboard reached nobody who already had the file. Re-running `lesysbot setup` is the upgrade path, so it has to actually deliver fixes) and then runs `apply.start_dashboard`, which is **never fatal**: if Docker is running (`_docker_running` = installed + `_compose_ok` + `_daemon_ok`) it asks a menu (auto-start the bundled stack now via `_run_bundled_stack` = `bash start.sh up`, vs do-it-manually); if Docker isn't ready it prints the exact no-sudo fix (install Docker Engine / start daemon / join `docker` group) plus the native-Grafana alternative (`GRAFANA_DOWNLOAD`). `LESYSBOT_SKIP_DASHBOARD` skips the whole step (unattended installs). **The flow asks *how* first (the auto/manual menu), then the Grafana username+password** LeSysBot should use (`ask_grafana_credentials`, defaults admin/admin, prev values from the saved file offered as defaults; the password prompt passes `secret=True` so `ui.text` masks the typed chars, the default hint, and the left-behind echo — never printed back anywhere either). The saved **URL is derived, never hardcoded**: `apply.grafana_port()` reads `GRAFANA_PORT` from the seeded `dashboard/.env` (the one place the port is set — it's what a user changes when something else owns 3000) and `default_grafana_url()` turns it into `http://localhost:<port>`, keeping a previously saved *non-local* URL (a deliberate remote Grafana) but letting the stack's port override a saved `localhost:` one — otherwise a stack on 3001 kept being advertised on 3000, where the impostor service answers. `_persist_grafana` then `write_grafana_env`s them to `~/.lesysbot/grafana.env` (0600) as `LESYSBOT_GRAFANA_{URL,USER,PASSWORD}` and `_apply_creds_to_stack_env`s the same admin login into the bundled `dashboard/.env` (`GF_SECURITY_ADMIN_*` first-boot only). `grafana.env` is read back at bot startup by `paths.load_grafana_env()` (called from `__main__._load_settings`, `os.environ.setdefault` so an explicit env wins; the password/token are then `add_secret`ed for log redaction) — that's how the `share_dashboard` tool and `status.detect_grafana` authenticate. `paths.parse_env_file` is the shared flat `KEY=VALUE` parser. It is **not part of the Python package** (not under `lesysbot/`, so hatchling bundles it as data, never as a module) and it does **not** reintroduce a listener into the bot — the stack runs as its own containers, everything binds **`127.0.0.1` only**, and it needs **no sudo** (`docker compose` runs unprivileged; upholds the same security/no-root stance as the rest of the repo). `uninstall.sh` offers to stop it with `start.sh down` (no `-v`, so Docker volumes survive). User docs live in `docs/dashboards.md`; `dashboard/README.md` is the stack's technical reference; the agent-facing skill is `skills/manage-dashboards/`.

**One compose file, because there is one way host metrics work here:**
- `docker-compose.yml` — Prometheus + Grafana + `node-exporter` (+ `nvidia-exporter` under `--profile gpu`) all on the **host network**, bound to localhost. Host networking is mandatory: `/proc/net/dev` is network-namespace-scoped, so a bridge container reports its own `eth0` instead of the host's real NICs; running everything host-net + localhost also sidesteps the `ufw`/iptables block on container→host traffic.

The Compose **project name stays `lesysbot-monitoring`** after the `monitoring/` → `dashboard/` rename: it is how `docker compose down` finds the containers it started, so renaming it would strand every already-running stack as untracked containers holding the ports.

The Grafana datasource URL is `${PROM_URL}` (Grafana interpolates env vars in provisioning files), injected by the compose as `http://127.0.0.1:9090`. Grafana provisions a **directory**, not a file: `./grafana/dashboards/generated` is mounted at `/var/lib/grafana/dashboards`, so several dashboards can coexist — `lesysbot dashboard render` writes every installed dashboard package there, and `start.sh` falls back to `gen-dashboards.py` (or to copying the committed portable JSON) when LeSysBot isn't installed. `dashboards.yml` has `disableDeletion: false`, so a dashboard that stops being rendered disappears on the next boot. **Dashboards are generated** — edit `scripts/gen-dashboards.py` (stdlib only) and regenerate, never hand-edit the JSON under `grafana/dashboards/`. The generator has two modes: bare, it rewrites the committed **portable** `system-overview.json`; `--host linux --have <caps> --out PATH` emits one **host-specific cut** (`build_linux` via `build_for`), which is what `start.sh` runs. Shared panels live in `cpu_section`/`swap_section`/`disk_section`/`network_section` so the two cuts can't drift from each other. `CAPABILITIES` is the capability vocabulary and an unknown capability is an argparse error — a typo in a start script must fail loudly rather than silently drop a dashboard row. The cut reuses the portable dashboard's `uid` (`lesysbot-node`) so re-running `start.sh` *replaces* the dashboard instead of accumulating near-duplicates.

**`start.sh` probes before generating**, because a panel querying a metric the host can't produce is visually identical to a broken panel — that ambiguity is the bug the whole mechanism exists to remove. `detect_capabilities_linux` reads chip names from `/sys/class/hwmon/*/name` (`coretemp|k10temp|zenpower|cpu_thermal` → `cpu_temp`, `nvme|drivetemp` → `disk_temp`, `amdgpu` → `amd_gpu`; AMD GPU temperature comes from hwmon and needs **no exporter**, unlike NVIDIA) plus `/sys/class/thermal/thermal_zone0` and `nvidia-smi`. **NVIDIA is keyed on `nvidia-smi`, never on the card** (`nvidia_gpu_exporter` shells out to it, so a driverless GPU is unscrapeable); `lspci` is consulted *only* to explain the omission and name the driver to install. The script then prints an "optional add-ons" block (the exact `modprobe` for a missing sensor driver) — suggestions, never run for the user, and suppressed inside a VM (`is_virtual`) where the advice would be a dead end. Generated files are `grafana/dashboards/generated-*.json` (git-ignored). Falling back to the committed portable JSON (no `python3`) always warns, because "whole rows are empty" then has a different cause than a real fault. `start.sh` `return 0`s when sourced instead of executed, which is the seam `tests/test_start_detect.py` drives against a fixture `/sys` tree via `SYSFS_ROOT` — so the detection logic is verified without the sensors being present. GPU metrics are `nvidia_smi_*` (labeled by `uuid` only → legends use `{{uuid}}`); temperatures come from `node_exporter` `hwmon`/`thermal_zone` via a `group_left` join onto `node_hwmon_sensor_label`/`node_hwmon_chip_names` (CPU = `coretemp|k10temp|cpu_thermal`, disk = `nvme|drivetemp`). `dashboard/{bin,run,native}/` and `.env` are git-ignored.

**Hardware-adaptation is the whole point, so several things auto-select at runtime.** `start.sh` preflights Docker (installed / Compose v2 / daemon reachable) and fails with a fix-it message instead of a stack trace. It picks the **GPU** path automatically: `--profile gpu` (containerised `nvidia_gpu_exporter`) when `docker info` shows the `nvidia` runtime, else a **native** GPU exporter via `run-exporters.sh` — so a GPU box without the nvidia-container-toolkit still gets GPU metrics instead of a crash-looping container. The portable dashboard asks for every sensor family a Linux box might have and leaves the absent ones empty; the probed cut omits them instead. When editing dashboard queries, keep the two builders in step — `tests/test_gen_dashboards.py` pins which panels each includes, plus a staleness check that the committed JSON still matches the generator.

The bundled **`tools/share-dashboard/`** package bridges the stack back to the bot: "share me the dashboard" publishes a public Grafana **snapshot** to `snapshots.raintank.io`. It builds the snapshot itself — pulls the dashboard model from Grafana, replays each panel's Prometheus queries via Grafana's datasource proxy (`/api/datasources/proxy/uid/<ds>/api/v1/query_range`), and bakes the results into **each panel target** as a `queryType:"snapshot"` frame list (modern Grafana data-frame JSON: `{schema:{fields:[Time, Value(labels)], meta}, data:{values:[[ms…],[…]]}}`, one entry per series) so the public copy renders on Grafana 11 without reaching back to your Prometheus. **Critical:** the older top-level `panel.snapshotData` format does *not* render on Grafana 11 — the data must live on each target, and the request is POSTed to **Grafana's own `/api/snapshots`** with `{dashboard, name, expires, external:true}` (auth'd), letting Grafana relay it to raintank and return the public `url` (plus a Grafana-side `deleteUrl`; delete is a GET on it). POSTing the baked model straight to raintank instead produces empty panels. **Because we now publish *through* Grafana, Grafana is the snapshot registry** — so `list_snapshots`/`delete_snapshot` build a combined list (`_combined_snapshots`): **`GET /api/dashboard/snapshots`** (Grafana's own `/dashboard/snapshots` page, authoritative) **plus** any *unexpired* snapshots recorded in `~/.lesysbot/dashboard_snapshots.json` that Grafana has since pruned ("orphans", flagged in the listing). Grafana prunes external-snapshot rows **aggressively** (snapshots created minutes apart were already absent from `/api/dashboard/snapshots` while only the newest survived), so a listing that trusted only the local file over-reported ghosts, while one that trusted only Grafana would hide still-live public links — hence the merge. `list_snapshots` prunes the local file of **expired** entries only (never live ones — that would discard their deleteKey). **Deletion is dual (`_delete_everywhere`):** `DELETE /api/snapshots/<key>` on Grafana when it still knows the key (also asks raintank to drop it), **and** a direct `GET {raintank}/api/snapshots-delete/<deleteKey>` — the key point being **the `deleteKey` returned at creation is raintank's own** (verified: it deletes on raintank independent of Grafana), so orphans Grafana forgot are still removable as long as we kept the deleteKey. raintank may serve a CDN-cached copy for up to ~1h after deletion (its delete response says so). Grafana creds come from `LESYSBOT_GRAFANA_USER`/`_PASSWORD`/`_TOKEN` (defaults `admin`/`admin`); its **location** is resolved by `_resolve_grafana` like `status.detect_grafana` — `LESYSBOT_GRAFANA_URL` only when `_is_grafana` confirms Grafana answers there, else probe `_candidates()` (the local `dashboard/.env` `GRAFANA_PORT` first, then 3000/3001). Trusting the override blindly meant a stale saved URL POSTed snapshots at whatever else now owns that port. Tests are network-free (`tests/test_share_dashboard.py` monkeypatches the module's `_grafana`/`_query_range`/`_post`/`_delete`/`_get`).
