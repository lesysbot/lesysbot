# Dashboard stack (`dashboard/`)

A **standard, self-contained Prometheus + Grafana stack** recording CPU / memory / disk / network (per-interface, so Ethernet vs Wifi) / temperatures / NVIDIA GPU as time series. It is **default, not optional**. It is **not part of the Python package** (not under `lesysbot/`, so hatchling never bundles it) and it does **not** add a listener to the bot — the stack runs as its own processes (containers, or brew services on macOS), everything binds **`127.0.0.1` only**, and it needs **no sudo** (`docker compose` and `brew` both run unprivileged).

Docs live in `dashboard/README.md`; the agent-facing skill is `skills/manage-dashboards/`; discoverable from the root `README.md` and `docs/README.md`.

## How `lesysbot setup` seeds and starts it

`apply.seed_dashboard` copies the stack into `~/.lesysbot/dashboard` — skipping `bin/`/`run/`/`native/`, copying `.env` from the example, and **refreshing shipped files whose contents differ while never touching the user's**. The split is `DASHBOARD_KEEP = (".env", "prometheus")`: ports/Grafana login and hand-added scrape targets are seeded once and then left alone forever; everything else is program code whose installed copy has no value except to be current. It deliberately does **not** bail out on `dst.exists()` — re-running `lesysbot setup` is the upgrade path, so it has to actually deliver fixes to already-installed machines (regression-tested in `tests/test_setup_wizard.py`).

`apply.start_dashboard` then runs, **OS-specific and never fatal**:

- **Linux** — if Docker is running (`_docker_running` = installed + `_compose_ok` + `_daemon_ok`) it asks a menu (auto-start via `_run_bundled_stack` = `bash start.sh up`, vs do-it-manually); otherwise it prints the exact no-sudo fix (install Docker Engine / start daemon / join `docker` group) plus the native-Grafana alternative.
- **macOS** — deliberately **does not require Docker Desktop**, and is fully automatic: `_grafana_macos` asks the same auto/manual menu, then `_run_brew_stack` runs `bash dashboard/scripts/install-macos.sh up`. With no Homebrew (`_brew_ready`) there is nothing to automate, so it names `brew.sh` (`BREW_INSTALL`) and falls through to `_grafana_manual_instructions`.
- **Windows** — deliberately **does not require Docker Desktop**: `_grafana_manual_instructions` instructs a native Grafana install from `grafana.com/grafana/download` (`GRAFANA_DOWNLOAD`) and how to connect it (auto-detected on `localhost:3000`, else `LESYSBOT_GRAFANA_URL`), mentioning the bundled stack only as a shortcut when Docker happens to be running.

`LESYSBOT_SKIP_DASHBOARD` skips the whole step (unattended installs).

**Credentials.** Each OS flow asks *how* first, then the Grafana username+password (`ask_grafana_credentials`, defaults admin/admin, previous values offered as defaults; the password prompt passes `secret=True` so `ui.text` masks the typed chars, the default hint and the left-behind echo — and it is never printed back anywhere). The saved **URL is derived, never hardcoded**: `apply.grafana_port()` reads `GRAFANA_PORT` from the seeded `dashboard/.env` (the one place the port is set) and `default_grafana_url()` turns it into `http://localhost:<port>`, keeping a previously saved *non-local* URL (a deliberate remote Grafana) but letting the stack's port override a saved `localhost:` one — otherwise a stack on 3001 keeps being advertised on 3000, where an impostor service answers. `_persist_grafana` writes them to `~/.lesysbot/grafana.env` (0600) as `LESYSBOT_GRAFANA_{URL,USER,PASSWORD}` and `_apply_creds_to_stack_env` puts the same admin login into `dashboard/.env` (`GF_SECURITY_ADMIN_*`, first-boot only). `paths.load_grafana_env()` reads it back at bot startup (from `__main__._load_settings`, `os.environ.setdefault` so an explicit env wins; the password/token are then `add_secret`ed for log redaction) — that is how `share_dashboard` and `status.detect_grafana` authenticate. `paths.parse_env_file` is the shared flat `KEY=VALUE` parser.

`uninstall.sh` detects which stack is present and offers to stop it — `install-macos.sh down` (brew services stopped, formulae left installed, with the `brew uninstall` line printed) and/or `start.sh down` (no `-v`, so Docker volumes survive); macOS can have both, so it asks once and stops whatever it finds.

## Three launch paths

**Two compose files, because host metrics need different plumbing per OS:**

- `docker-compose.linux.yml` — **Linux**: Prometheus + Grafana + `node-exporter` (+ `nvidia-exporter` under `--profile gpu`) all on the **host network**, bound to localhost. Host networking is mandatory: `/proc/net/dev` is network-namespace-scoped, so a bridge container reports its own `eth0` instead of the host's real NICs; host-net + localhost also sidesteps the `ufw`/iptables block on container→host traffic.
- `docker-compose.yml` — **macOS/Windows** (Docker Desktop): Prometheus + Grafana on a bridge; exporters run **natively** (auto-downloaded by `scripts/run-exporters.{sh,ps1}`) and are scraped via `host.docker.internal`.

**Plus a third, Docker-free path on macOS — `scripts/install-macos.sh`**, which is what `lesysbot setup` runs there (the compose file stays for anyone who prefers containers; the script refuses to start when it sees `lesysbot-*` containers running, since both bind the same ports). It brew-installs `grafana`/`prometheus`/`node_exporter` and runs them under `brew services`, so the whole stack survives a reboot without a daemon. Everything it *generates* lands in `dashboard/native/` (git-ignored — the paths are absolute and machine-specific), rewritten from scratch on every run: a Prometheus scrape config on plain `localhost` (no `host.docker.internal` hop) and Grafana provisioning with the datasource URL **baked in** (there is no compose to interpolate `${PROM_URL}`).

Wiring the brew formulae up takes three different mechanisms, each forced by how the formula is packaged:

- `prometheus`/`node_exporter` read their flags from `$(brew --prefix)/etc/<name>.args` — a `$(<file)` expansion, so those files **cannot carry a comment** marking them ours; hence the `.args.lesysbot` stamp file the backup check diffs against, which is what stops a re-run from "backing up" its own output.
- Grafana is launched with a fixed `--config`, so the script appends a delimited `;;; BEGIN LeSysBot ;;;` block to `grafana.ini` (later sections/keys win in Grafana's ini parser) — the shipped file is never edited, only appended to, and the block is replaced wholesale on re-run.
- The admin password goes through `grafana cli admin reset-admin-password --password-from-stdin` with the server stopped, because `[security] admin_password` in `grafana.ini` only applies when the DB is first created (so it can't fix an existing Grafana) and would mean a cleartext password in a shared `etc/` file.

Ports/credentials come from `dashboard/.env`, the same file the compose stacks read, so `apply.grafana_port()` keeps deriving the saved URL correctly.

The script **preflights the ports** after stopping its own services (so a re-run doesn't flag itself) and `die`s naming the process that holds one — a busy port is otherwise silent, since `brew services` just parks the service in `error` state and the dashboard renders empty panels; 9090 is a common clash (VS Code listens there). The closing report verifies **Prometheus as well as Grafana** and the script exits non-zero when either is down, so `_run_brew_stack` reports it rather than claiming success. Two `set -e` traps to respect when editing it: `set -o pipefail` means `lsof` exiting 1 on a free port propagates out of `owner="$(port_owner …)"` and kills the script before any caller sees the empty result (hence the `|| true` inside `port_owner`), and it targets **bash 3.2** (macOS' `/bin/bash`), where a bare `$var` immediately followed by a non-ASCII character parses as part of the variable name — so interpolations adjacent to `…`/`—` must be braced.

## Provisioning: one directory, many dashboards

All three launch paths point Grafana at **`grafana/dashboards/generated/`** — a *directory*, not one file. Grafana's file provider loads every JSON it finds there. **LeSysBot keeps exactly one dashboard** (`generated/lesysbot.json`, at the fixed uid `lesysbot`) and sweeps every other JSON out of that directory on each render — so the directory-not-a-file shape is what lets the *standalone* start scripts write a host-named cut here on a machine with no LeSysBot, not a way to run several at once. It has to be that subdirectory and not `grafana/dashboards` itself: the committed portable cuts live one level up, and provisioning those would put the Windows dashboard on a Mac, permanently empty. The compose mounts are read-only, so Grafana UI edits are accepted and reverted on the next provision — the durable way to change a dashboard is to edit its package and re-render.

The directory is filled by three routes, best first: `lesysbot dashboard render` (every *installed* dashboard package, so a user's own dashboards come up alongside System Overview) → `gen-dashboards.py` for this host (LeSysBot not on PATH, e.g. running from a checkout) → the committed portable JSON (no `python3` at all). **Falling back always warns**, because "whole rows are empty" then has a different cause than a real fault. The directory is created either way: Docker creates a missing bind-mount source as a root-owned directory, which then can't be written without sudo. `dashboard/{bin,run,native}/`, `grafana/dashboards/generated/` and `.env` are git-ignored.

The Grafana datasource URL is `${PROM_URL}` (Grafana interpolates env vars in provisioning files); each compose injects it (`http://prometheus:9090` bridge vs `http://127.0.0.1:9090` linux), so one datasource file serves both. Its fixed uid `prometheus` is what every bundled dashboard binds its panels to. `dashboards.yml` has `disableDeletion: false`, so a dashboard that stops being rendered disappears on next boot.

## Generating dashboards

**Dashboards are generated** — edit `scripts/gen-dashboards.py` (stdlib only) and regenerate; never hand-edit the JSON under `grafana/dashboards/`. Two modes: bare, it rewrites the two committed **portable** JSONs; `--host {linux,macos,windows} --have <caps> --out PATH` emits one **host-specific cut** (`build_linux`/`build_macos`/`build_windows` via `build_for`), which is what every start script runs. Shared panels live in `cpu_section`/`swap_section`/`disk_section`/`network_section` so the cuts can't drift. `CAPABILITIES` is the per-host vocabulary and an unknown capability is an argparse error — a typo in a start script must fail loudly rather than silently drop a dashboard row. Every cut carries the same `DASHBOARD_UID` (`lesysbot`) — the value `lesysbot/dashboards/render.py` also stamps — so a machine has one dashboard at `/d/lesysbot` whichever route wrote the file, and switching routes *replaces* it instead of accumulating near-duplicates. Generating per host is what keeps one generator covering every hardware combination without committing a JSON per combination; `tests/test_gen_dashboards.py` pins the inclusion/exclusion decisions and fails when the committed JSONs go stale.

**Each start script probes before generating**, because a panel querying a metric the host can't produce is visually identical to a broken panel — that ambiguity is the bug the whole mechanism exists to remove.

- `start.sh` (`detect_capabilities_linux`) reads chip names from `/sys/class/hwmon/*/name` (`coretemp|k10temp|zenpower|cpu_thermal` → `cpu_temp`, `nvme|drivetemp` → `disk_temp`, `amdgpu` → `amd_gpu`; AMD GPU temperature comes from hwmon and needs **no exporter**, unlike NVIDIA) plus `/sys/class/thermal/thermal_zone0` and `nvidia-smi`. It `return 0`s when sourced instead of executed, which is the seam `tests/test_start_detect.py` drives against a fixture `/sys` tree via `SYSFS_ROOT` — so Linux-only detection logic is verified on macOS and Linux CI alike.
- `start.ps1` asks the **running** `windows_exporter` whether it actually serves `windows_thermalzone_*`, since that is a firmware property and no static rule gets it right.
- `install-macos.sh` detects `uname -m` → `MAC_ARCH`/`MAC_KIND`, `has_nvidia` (`nvidia-smi` on PATH) and `has_gpu_die_temp` (**runs the collector** and greps its output — see the die-temperature paragraph below for why nothing cheaper is correct), turns them into a capability list via `dashboard_caps()`, and must **never** swallow the generator's stderr — an invisible argparse exit-2 silently drops every Mac onto the portable dashboard. `tests/test_install_macos.py` pins its flags against the generator, as `tests/test_start_detect.py` does for `start.sh`; keep its sourcing guard for that reason.

**NVIDIA is keyed on `nvidia-smi` everywhere, never on the card** (`nvidia_gpu_exporter` shells out to it, so a driverless GPU is unscrapeable); `lspci`/`Win32_VideoController`/`system_profiler` are consulted *only* to explain the omission and name the driver to install. The same flag gates the `nvidia_gpu` scrape job, and on macOS section 4c starts that exporter through `run-exporters.sh nvidia` with `EXPORTER_BIND=127.0.0.1` (that script's macOS default is `0.0.0.0` for the Docker Desktop VM hop). Both scripts print an "optional add-ons" block (the exact `modprobe` for a missing Linux sensor driver, LibreHardwareMonitor on Windows, a die-temp helper on macOS) — suggestions, never run for the user, and suppressed inside a VM (`is_virtual`) where the advice would be a dead end.

**On Linux the GPU path auto-selects:** `--profile gpu` (containerised `nvidia_gpu_exporter`) when `docker info` shows the `nvidia` runtime, else a **native** GPU exporter via `run-exporters.sh` — so a GPU box without the nvidia-container-toolkit still gets GPU metrics instead of a crash-looping container. `start.{sh,ps1}` also preflight Docker (installed / Compose v2 / daemon reachable) and fail with a fix-it message instead of a stack trace.

## Metric names and panel queries

GPU metrics are `nvidia_smi_*` (labeled by `uuid` only → legends use `{{uuid}}`); temperatures come from `node_exporter` `hwmon`/`thermal_zone` via a `group_left` join onto `node_hwmon_sensor_label`/`node_hwmon_chip_names` (CPU = `coretemp|k10temp|cpu_thermal`, disk = `nvme|drivetemp`). Coverage is Linux-rich, battery-plus-optional-die on macOS, ACPI-best-effort on Windows.

**Keep the `or`-fallbacks when editing queries — dropping one silently blanks a panel on another OS.** macOS `node_exporter` uses different metric names, so memory panels fall back (`node_memory_MemAvailable_bytes`/`MemTotal_bytes` → `node_memory_active/wired/compressed/total_bytes`); the Windows total-RAM metric `or`s `windows_cs_physical_memory_bytes`/`windows_memory_physical_total_bytes` across exporter versions; swap is **not** Linux-only (macOS names them `node_memory_swap_{used,total}_bytes` against Linux' `SwapFree`/`SwapTotal`), so the portable panel `or`s both. macOS-absent readings (disk I/O, some temperatures) just stay empty.

The macOS additions follow the same split: CPU/GPU temperature **stat tiles** `or` the `macos_*` series onto the hwmon ones (exactly one side has data on a given host, so one tile serves both), but Apple GPU gets a **row of its own** (`gpu_section_apple`) rather than being `or`-ed into the NVIDIA panels — the two sources label series differently (`uuid` vs `engine`), so a merged panel would lose its legend on one OS. On the *macOS* cut that row is the main GPU row (retitled via `gpu_section_apple(title=…)`) and the NVIDIA one is omitted.

## macOS metrics collector (`scripts/macos-metrics.py`)

`node_exporter` has no GPU support on macOS and its `thermal` collector exposes CPU *throttling* ratios (`node_thermal_cpu_speed_limit_ratio`, `…_scheduler_limit_ratio`, `…_available_cpu`) rather than any temperature, through an Intel-only API (on Apple Silicon it reports `node_scrape_collector_success{collector="thermal"} 0`) — hence the Intel-only throttling panels in `temps_section_macos`, and why GPU and temperature rows need this collector at all.

The script (stdlib only) reads `ioreg` for Apple GPU utilization/memory (`IOAccelerator` → `PerformanceStatistics`) and battery temperature (`AppleSmartBattery`, hundredths of a °C), and writes `macos_*` samples **atomically** (tmp + rename, since node_exporter may read mid-write) into `native/textfile/`, served via `--collector.textfile.directory`. A **launchd agent** (`com.lesysbot.macos-metrics`, `StartInterval` 15 s) re-runs it — a one-shot script needs a timer, and launchd also brings it back after a reboot like the brew services around it; its interpreter is pinned to brew's or `/usr/bin/python3` rather than whatever `command -v python3` finds, because launchd has a minimal PATH and a conda/venv python can vanish. **The optional die-temp helpers need the same treatment and it is easy to miss**: launchd hands the job `PATH=/usr/bin:/bin:/usr/sbin:/sbin`, so a Homebrew `macmon`/`smctemp` is invisible to a bare exec — it works when the script is run by hand and never under the agent, and `_run` swallows the `FileNotFoundError` as "tool not installed", so the only symptom is a permanently empty tile. `_run` therefore resolves `cmd[0]` through `_resolve()` (PATH, then `/opt/homebrew/bin` and `/usr/local/bin`); every command goes through that one choke point. Because a textfile keeps being served after the writer dies, it emits `macos_metrics_last_run_timestamp_seconds` (formatted with `repr()`, not `%g` — 6 significant digits mangles a Unix timestamp by hours) and `status` reports the sample's **age** rather than merely that the file exists.

CPU/GPU **die** temperatures are deliberately absent: Apple exposes them only via IOReport (private framework) or root-only `powermetrics`, so the collector opportunistically reads `smctemp`/`macmon` if the user installed either — the no-sudo rule wins over completeness. The two tiles are then treated **differently, on purpose**: the CPU tile ships on every Mac and stays empty until a helper is installed, because that emptiness is *actionable* and its description names the fix. The GPU tile is a probed capability (`gpu_die_temp`) and is **omitted** where the reading cannot be produced, because there its emptiness is not actionable — measured on an M1/macOS 26, `macmon` reports 0 for the GPU (its IOReport `GPU Stats :: Temperature` channels read 0 there) and `smctemp` 0.7.0 `-g` returns 0.0 even under full GPU load with its own suggested `-i25 -n180 -f` flags, while the SMC's `GPU MTR Temp Sensor*` do track load (~70 °C at 100% GPU) but snap to exactly 30.00 the instant the GPU power-gates — a placeholder, not a cooling curve. So neither the chip nor "a helper is installed" predicts it, and the only correct probe is running the collector and looking for the metric. Section 1a of the installer **offers** to install one, arch-aware (`macmon` is `arch: :arm64`, so an Intel Mac is only offered `smctemp`, and an explicit `LESYSBOT_TEMP_HELPER=macmon` there is downgraded to `smctemp`). The prompt **defaults to no**, is skipped when stdin isn't a TTY (`[ -t 0 ]`), can be answered up front with `LESYSBOT_TEMP_HELPER=macmon|smctemp|none`, and a failed `brew install` warns rather than failing the stack. **Neither helper may become a dependency**: `smctemp` is a personal tap (`macmon` reached homebrew-core) and they fail on ordinary machines (brew refuses them on an outdated Xcode; `smctemp` compiles from source so it also needs Command Line Tools). "Offer, never require" is the whole point — a hard step there would break the enter-through-the-prompts install.

macmon's JSON layout is not a stable contract, so `_find_temps` walks the parsed object matching on key *names* anywhere in the tree rather than a fixed path — a pinned path would silently break on upgrade into an empty panel nobody notices. `tests/test_macos_metrics.py` loads the script by path (it's outside the wheel), stubs `_run`, and pins the parsing against recorded `ioreg` output plus several plausible macmon shapes, so it verifies on Linux CI where neither tool can exist.

## `tools/share-dashboard/`

The bundled package that bridges the stack back to the bot: "share me the dashboard" publishes a public Grafana **snapshot** to `snapshots.raintank.io`.

It builds the snapshot itself — pulls the dashboard model from Grafana, replays each panel's Prometheus queries via Grafana's datasource proxy (`/api/datasources/proxy/uid/<ds>/api/v1/query_range`), and bakes the results into **each panel target** as a `queryType:"snapshot"` frame list (data-frame JSON: `{schema:{fields:[Time, Value(labels)], meta}, data:{values:[[ms…],[…]]}}`, one entry per series) so the public copy renders on Grafana 11 without reaching back to your Prometheus. **Critical:** the top-level `panel.snapshotData` format does *not* render on Grafana 11 — the data must live on each target, and the request is POSTed to **Grafana's own `/api/snapshots`** with `{dashboard, name, expires, external:true}` (auth'd), letting Grafana relay it to raintank and return the public `url` (plus a Grafana-side `deleteUrl`; delete is a GET on it). POSTing the baked model straight to raintank instead produces empty panels.

**Because publishing goes *through* Grafana, Grafana is the snapshot registry** — so `list_snapshots`/`delete_snapshot` build a combined list (`_combined_snapshots`): **`GET /api/dashboard/snapshots`** (authoritative) **plus** any *unexpired* snapshots recorded in `~/.lesysbot/dashboard_snapshots.json` that Grafana has since pruned ("orphans", flagged in the listing). Grafana prunes external-snapshot rows aggressively, so trusting only the local file over-reports ghosts while trusting only Grafana hides still-live public links — hence the merge. `list_snapshots` prunes the local file of **expired** entries only (never live ones — that would discard their deleteKey).

**Deletion is dual (`_delete_everywhere`):** `DELETE /api/snapshots/<key>` on Grafana when it still knows the key (which also asks raintank to drop it), **and** a direct `GET {raintank}/api/snapshots-delete/<deleteKey>` — the key point being **the `deleteKey` returned at creation is raintank's own**, so orphans Grafana forgot are still removable as long as we kept it. raintank may serve a CDN-cached copy for up to ~1h after deletion.

Grafana creds come from `LESYSBOT_GRAFANA_USER`/`_PASSWORD`/`_TOKEN` (defaults `admin`/`admin`); its **location** is resolved by `_resolve_grafana` like `status.detect_grafana` — `LESYSBOT_GRAFANA_URL` only when `_is_grafana` confirms Grafana answers there, else probe `_candidates()` (the local `dashboard/.env` `GRAFANA_PORT` first, then 3000/3001). Trusting the override blindly means a stale saved URL POSTs snapshots at whatever else now owns that port. Tests are network-free (`tests/test_share_dashboard.py` monkeypatches `_grafana`/`_query_range`/`_post`/`_delete`/`_get`).
